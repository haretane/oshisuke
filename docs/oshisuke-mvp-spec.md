# 推しスケ MVP仕様書

- バージョン: 0.1
- 作成日: 2026-08-29
- 状態: 要件整理中（実装前）
- 正式表記: 推しスケ / OSHISUKE

## 1. サービス概要

「推しスケ」は、ファンみんなで推しの情報を育て、その中から自分に必要なものだけを自分のスケジュールとして管理するWebサービスである。

共有情報は投稿者個人の所有物ではなく、Wikipediaのように複数のユーザーが情報を追加・更新して完成度を高めていく。

サービスの中心体験は次のとおり。

1. 推しを探して登録する
2. 推しの共有カードを見る
3. 新しいカードを追加し、既存カードを更新する
4. 必要なカードを「⇨マイスケジュール」する
5. 「チェック」で気になる予定を管理する
6. 「コミット」で自分の確定予定として管理する

## 2. 重要な用語

- **推し**: 人物、グループ、作品、キャラクターなど、ユーザーが情報を追いたい対象
- **カード**: ライブ、発売、配信などの共有情報
- **公演・開催枠**: ツアーや複数部制イベントに含まれる個別の日程
- **マイスケジュール**: ユーザーが選んだ共有カードへの参照
- **チェック**: 気になる、確認したい、参加するかもしれない状態
- **コミット**: 自分の予定として確定した状態
- **推し友**: 将来追加予定の、相互承認型のユーザー同士のつながり（暫定名称）

「マイスケ」という略称と「＋スケジュール」という操作名は使用しない。

## 3. 公開範囲とログイン

### 3.1 ログイン不要

- ホームおよび共有カードの閲覧
- 推し検索
- 推しプロフィールの閲覧
- カード詳細の閲覧
- セットリストの閲覧

### 3.2 ログイン必須

- 推し登録と個人設定
- カードの追加・更新
- 推しプロフィールの追加・更新
- 編集案への確認
- 「⇨マイスケジュール」
- チェック・コミット・一覧から外す
- 通報

未ログイン状態でログイン必須操作を選んだ場合はログイン画面へ案内し、ログイン後に可能な限り元のページへ戻す。

### 3.3 認証方式

- MVPはメールアドレスとパスワードを使用する
- PHPの安全なセッションCookieを使用する
- 開発中はメール送信なしで確認できる段階を設ける
- 一般公開前にメール認証とパスワード再設定を追加する
- Googleログイン等は将来追加できる設計とする

## 4. 主要画面とナビゲーション

### 4.1 スマートフォン下部ナビ

1. **推し検索**: 推しプロフィールを検索
2. **OSI**: ホーム。登録した推したちの共有カードを表示
3. **マイスケジュール**: 自分が選んだカードを表示

下部ナビは左から「推し検索」「OSI」「マイスケジュール」の順に配置する。「OSI」は将来、独自の画像・SVGデータへ差し替える。見た目が画像だけでも、支援技術には「ホーム」と伝える。

「カードを追加」は下部ナビへ置かず、各推しページと必要に応じてホームへ補助操作として置く。

### 4.2 画面上部の補助操作

- お知らせ: ベル型SVG
- アカウント設定: 設定用SVG

### 4.3 ホーム

- ログイン後の基本入口とする
- 登録した複数の推しの共有カードを混在表示する
- 新着・日程・人気を切り替える
- 推しを横方向の選択肢から1人に絞り込める
- 「すべて」は登録したすべての推しを意味する

推し未登録時は、無関係な共有カードを並べず、推し検索へ案内する。

### 4.4 マイスケジュール

- 「チェック」「コミット」の2状態をタブで切り替える
- 複数の推しの予定を日時順に混在表示する
- 「すべて」タブは置かない
- 開催済みのカードは削除せず「過去の予定」で確認できる

### 4.5 推しページ

- 推しプロフィール
- 「推しに登録」
- 「＋ カードを追加」
- 新着・日程・人気
- カード表示とカレンダー表示
- その推しのカードだけを対象とする検索

## 5. 推しプロフィール

### 5.1 推しの種類

- 人物
- グループ
- 作品
- キャラクター
- その他

### 5.2 基本情報

- 正式名称
- 略称（ホームの推しタブ等、狭い場所で使用）
- 読み方
- 別名・英語表記
- 種類
- 複数の推しカテゴリ
- 短い紹介
- 初期アイコン
- 初期カラー
- 複数の公式リンク
- 作成者、更新者、作成日時、更新日時（内部管理）

公式リンクは公式サイト、X、YouTube、Instagram等を複数登録できる。追加・変更・削除は共同編集の対象とする。

### 5.3 アイコンとカラー

- ユーザーがアップロードするプロフィール画像はMVPに含めない
- 推しスケが用意したSVGアイコンから、プロフィール作成者が初期アイコンを選ぶ
- プロフィール作成者が初期カラーも選ぶ
- 共有の初期アイコン・カラーは共同編集対象とする
- アイコンはプロフィールの雰囲気を表す装飾であり、種別を確定する情報として扱わない
- 企業ロゴ、作品ロゴ、実在人物の顔に似せた素材は用意しない

推し登録したユーザーは、自分の画面だけでアイコンとカラーを変更できる。個人変更には投票を必要としない。

表示時は個人設定があれば個人設定を使い、なければ共有の初期設定を使う。「初期設定に戻す」も用意する。

### 5.4 推し登録

- 「推しに登録」は1回の操作で完了する
- 登録時は共有プロフィールの初期アイコン・カラーを使用する
- 登録後に「アイコン・カラーを変更」を案内できる
- 推し登録解除後も、マイスケジュールと個人設定は保持する
- 再登録時は以前の個人設定を復元する

### 5.5 推しプロフィールの新規作成

- 検索して見つからない場合、ログインユーザーが作成できる
- メール認証済みユーザーのみ作成可能
- 登録7日未満は1日3件まで
- 同名、類似名、公式URL一致の候補を作成前に表示する

### 5.6 推し同士の関係

推し同士の関係は多対多で管理する。

例:

- メンバーBがグループAとグループCに所属
- 声優AがキャラクターCを担当
- キャラクターCが作品Bに登場
- スピンオフ作品が親作品と関連

関係には種類、開始日、終了日、現在の状態、補足、編集履歴を持てるようにする。

所属関係だけを理由に、グループのすべてのカードをメンバー本人のカードとして自動表示しない。イベントと推しの関係は実際の出演・関連に応じて明示的に登録する。

### 5.7 アニメ・作品の扱い

- アニメ作品と声優は別の推しプロフィールとする
- キャラクターも独立した推しとして登録できる
- 第1期、第2期、劇場版等は原則として同じ作品プロフィールにまとめる
- 期や劇場版等はカードのタイトル・概要で表現し、MVPでは専用区分を設けない
- 単独で推し登録することが自然なほど独立したスピンオフのみ、別プロフィールとして関連付けられる

## 6. 推し検索

### 6.1 検索対象

下部ナビの「推し検索」は推しプロフィールだけを検索する。共有カードの横断検索は行わない。

検索対象:

- 正式名称
- 読み方
- 別名
- 英語表記
- 推しカテゴリ

### 6.2 推しカテゴリ

推しは複数カテゴリを持てる。

人物・グループ系候補:

- アイドル
- アーティスト
- バンド
- 声優
- 俳優
- タレント
- お笑い
- ダンサー
- スポーツ
- クリエイター
- VTuber
- その他

作品・キャラクター系候補:

- アニメ
- 漫画
- ゲーム
- 映画
- ドラマ
- 舞台
- 小説
- キャラクター
- その他

### 6.3 検索前の候補表示

推し未登録ユーザー:

- カテゴリから探す
- 最近人気の推し
- 最近追加された推し

推し登録済みユーザー:

- カテゴリから探す
- あなたへのおすすめ
- 最近人気の推し

「最近人気」は直近30日間の新規推し登録数を基本とし、メール認証済みユーザーの登録だけを集計対象とする。人数表示は必須としない。

おすすめは当初、所属、出演、関連作品、共通カテゴリ等から算出し、AIを必要としない。将来、匿名化され十分な件数がある組み合わせに限り、併せて登録されることが多い推しを利用できる。

## 7. カードの基本構造

### 7.1 共通情報

- タイトル
- 主カテゴリ
- カード種類
- 関連する推し（将来の合同イベントを考慮し多対多）
- 概要・内容
- 日程または日程未定
- 情報元
- 特典の有無と内容
- ハッシュタグ
- 開催状態
- 作成者、更新者、日時（内部管理）

### 7.2 カテゴリ

カテゴリは運営側が管理する。一般ユーザーが自由にカテゴリを追加しない。

| 内部コード | 画面表示 |
|---|---|
| `live` | ライブ |
| `event` | イベント |
| `ticket` | チケット |
| `goods` | グッズ |
| `media` | メディア出演 |
| `stream` | 配信 |
| `release` | 発売 |
| `other` | その他 |

1カードの主カテゴリは1つとする。カテゴリは共通色のSVGアイコンと日本語ラベルで示し、カテゴリ別の色分けは行わない。

### 7.3 特典

- 特典あり
- なし・不明
- 特典内容（任意の自由記述）

特典の有無はカード種類を問わず検索できる専用項目とする。映画の場合は入場者特典、作品発売の場合は店舗別購入特典等を含む。

### 7.4 ハッシュタグ

- 最大10個
- 検索・整理のために使用する
- 推し名、日付、地域、カテゴリ等の専用項目をタグへ依存させない
- 既存タグを入力候補として表示する
- `#` の有無、重複、表記を保存時に正規化する
- カード一覧では一部を表示し、詳細ですべて確認できる
- タグ数ランキングや、タグを付けたユーザー名は表示しない
- 他人によるタグ追加・削除は共同編集の対象とする

## 8. カード種類と入力項目

カード追加の最初に「どんなカードを追加しますか？」と尋ね、選択内容に応じて入力欄を変える。

### 8.1 ライブ・コンサート

- 開催日／日程未定
- 開場時間（任意）
- 開演時間（任意）
- 終演予定（任意）
- 会場（任意）
- 都道府県・地域（任意）
- 内容（任意）
- 特典
- ハッシュタグ
- 情報元

### 8.2 ツアー

- 内容
- 特典
- ハッシュタグ

### 8.3 イベント

イベント種類候補:

## 9. カード追加と重複確認

操作名は「投稿」ではなく **「カードを追加」** とする。

カード追加中、タイトルや情報元を入力した時点で似たカードを表示する。

比較対象:

- 同じ推し
- 同じ、またはリダイレクト後が同じURL
- 似たタイトル
- 同じ日付
- 同じ会場

候補から既存カードを開き、「情報を更新」または「関連情報を追加」へ進める。自動的に重複と断定せず、「新しいカードとして続ける」ことも可能とする。

## 10. カード一覧表示

### 10.1 共通表示

- カテゴリSVGと日本語ラベル
- 推し名（ホームでは表示、推しページでは省略可能）
- タイトル
- 主な日付・時刻または「日程未定」
- 会場・地域等の主要情報
- サムネイル
- 主な情報元のページ名称とドメイン
- ハッシュタグ最大3件程度と残件数
- 「⇨マイスケジュール」または現在状態

概要全文、詳細な参加条件、全情報元等は詳細表示で確認する。

### 10.2 背景と推しカラー

- 共有カード: 白
- チェック: クリーム系
- コミット: オレンジ寄り
- 推しカラー: 枠、左端ライン、推し名横等のアクセント

色はCSS変数等で変更可能にし、状態は色だけでなく文字・形でも示す。

### 10.3 詳細表示

第一候補は、カードが画面全体へ広がるように見える縦長詳細表示とする。技術的には固有URLを持つ詳細ページとし、戻った際に一覧のスクロール位置とタブを復元する。

実装前モックで次を比較して最終決定する。

- 一覧内でカードが縦に展開
- 全画面へカードが展開

ツアーの公演展開は一覧内で利用可能とする。

## 11. 並び替えと人気

### 11.1 新着

共有カードの追加・重要更新日時を基準とする。具体的な更新の扱いは実装前に詰める。

### 11.2 日程

- 日程未定の情報を先頭に独立表示する
- 以降は日時順に表示する
- ツアーの各公演を正しい日付位置に表示する

### 11.3 人気

独立した「いいね」はMVPで設けない。

人気は、マイスケジュールへ登録したユニークユーザー数で決める。チェックとコミットはどちらも1人として数え、状態変更で二重計上しない。

- 通常は未開催または日程未定の情報を対象とする
- ツアー全体では同じユーザーを1人として数える
- 各公演の登録数は別途算出できる
- 「過去も含める」を選択できる
- 過去の期間は「今年」「過去12か月」「すべて」を用意する

## 12. カレンダー

- ホーム、推しページ、マイスケジュールに配置する
- カード表示を標準とし、カレンダーは補助表示とする
- 画面右端に丸いカレンダーSVGボタンだけを置く
- 常時表示の文字と初回チュートリアルは置かない
- ツールチップ、読み上げラベル、キーボード操作、十分なタップ領域を用意する
- カレンダー表示中はカード表示へ戻るSVGへ切り替える
- 月曜日始まりの7列グリッドとする
- 1日最大3件を表示し、超過時は残件数付きのMOREを表示する
- スマートフォンでは短い表示とし、日付マス全体から日別一覧を開ける
- 日程未定情報はカレンダー上部から別途確認する

共有カレンダーの表示優先順位:

1. 自分がコミットしている
2. 自分がチェックしている
3. その他をマイスケジュール登録人数順

マイスケジュールの表示優先順位:

1. コミット
2. チェック
3. 開始時刻順
4. 時刻未定

## 13. マイスケジュールとスワイプ

マイスケジュールは共有カードのコピーではなく、共有カードまたは公演への参照とユーザー固有状態を保持する。

### 13.1 共有画面

- 右スワイプ: マイスケジュールへ追加し、初期状態はチェック
- 明示的な「⇨マイスケジュール」ボタンも必ず用意する

### 13.2 マイスケジュール

- チェック状態で右スワイプ: コミット
- 左スワイプ: マイスケジュールから外す
- コミットからチェックへ戻す操作も用意する
- 共有カードそのものは削除しない

### 13.3 誤操作対策

- 横移動が縦移動より明確に大きい場合だけ横スワイプとして扱う
- 一定距離を超えた場合だけ確定する
- 指を離す前に実行内容を視覚表示する
- 操作後は確認ダイアログを出さず、「元に戻す」を短時間表示する
- すべてのスワイプ操作にボタン等の代替手段を用意する

### 13.4 ツアー

- まとめ状態のツアーを追加: その時点の全公演を追加
- 展開後に個別公演を追加: 選んだ公演だけ追加
- 一括追加を識別できる情報を保持する
- 後日追加された新公演は自動追加しない
- マイスケジュールで新公演追加を知らせ、ユーザーが選んで追加する

## 14. 開催状態と過去の予定

共有カードは次の状態を持つ。

- 開催予定
- 延期
- 中止
- 終了

延期・中止はマイスケジュール登録者へ知らせる。中止カードも削除せず明示して履歴に残す。

日付から判定できる場合は終了を自動判定し、日程未定の場合は共同編集で更新する。

開催済みカードは通常のチェック・コミット表示から外し、「過去の予定」で確認できる。状態とセトリ等は保持する。

## 15. 情報元URLとOGP

### 15.1 基本方針

イベントのタイトル、概要、日程等はユーザーが入力する。URLから投稿内容を自動確定しない。

URLから取得する情報:

- サムネイル候補（主に `og:image`）
- ページ名称（`og:title` またはHTMLの `title`）
- ドメイン
- 正規URL候補

ページ名称はイベントタイトルではなく、リンク先の説明として表示する。

### 15.2 複数の情報元

1カードへ複数URLを登録できる。

- 主な情報元
- 関連情報

ティザーから正式LPへ移行した場合、正式LPを主な情報元とし、ティザーは関連情報と履歴へ残す。URLを単純に上書きしない。

関連情報へのURL追加は原則として即時反映できる。ただし、主な情報元の変更は安全性と権限に応じて確認を通す。

推しプロフィールに登録された公式ドメインからの正式ページは、信頼判断に利用できる。異なるドメインを一律拒否しない。

### 15.3 URLなし

URLは強く推奨するが必須としない。URLなしの場合は情報を確認した場所を説明できる。

例:

- 会場での告知
- テレビ・ラジオ内での告知
- 店頭・会場掲示
- 雑誌・紙媒体
- その他

### 15.4 URLの保存

- ユーザーが入力した元URL
- リダイレクト後の最終URL
- ページが示す正規URL
- 実際にユーザーが開くURL

を分けて保持できる設計とする。画面には最終的なページ名称とドメインを分かりやすく表示する。

### 15.5 OGPサムネイル

- 取得結果をカード追加前に表示する
- 「この画像を使う」「画像を使わない」を選べる
- 取得失敗または不使用時はカード種類別のSVGプレースホルダーを表示する
- ユーザーによる画像アップロードはMVPに含めない
- 将来、取得画像をリサイズ、WebP化、圧縮してキャッシュする
- キャッシュ方針は著作権、利用規約、robots等を確認してから有効化する

### 15.6 SSRF等への対策

サーバーから外部URLへアクセスする前に、次を行う。

- HTTP・HTTPS以外を拒否
- localhost、private IP、link-local、特殊IPを拒否
- IPv4・IPv6の両方を確認
- DNS解決後の全IPを確認
- リダイレクト先を毎回再確認
- 接続時間、全体時間、取得容量を制限
- 不自然なURL、認証情報入りURL等を拒否
- OGP取得回数を制限
- 取得失敗時も手入力でカードを追加可能にする

## 16. 将来のアフィリエイト

MVPでは通常リンクとして扱う。将来、アニメイト、AMNIBUS、楽天市場等へショップ単位で対応できるようにする。

- 元URLは上書きせず保持する
- 対応を許可したショップだけ変換する
- 同じ商品だと確認できる場合だけ変換する
- ショップ・ASPごとの最新規約を確認する
- アフィリエイトリンクであることを明瞭に表示する
- 変換失敗時は通常の正規URLへ戻す
- 転売、非公式品、不明なショップは自動変換しない

## 17. 共同編集

### 17.1 基本ルール

- 作成者本人による更新は即時反映
- 他人による変更は編集案として保存
- 変更前と変更案を上下に並べて比較
- 編集者本人は自分の編集案へ確認できない
- メール認証済みかつ登録7日以上のユーザーだけ確認可能
- 同じユーザーは1編集案につき1回だけ判断できる
- 「編集案が正しい」2件で反映
- 「現在の内容が正しい」2件で却下
- 1対1は保留
- 管理者は確定・却下できる
- 必要件数は将来設定変更できる

確認画面では編集者のHNを目立たせず、内容と情報元を中心に判断する。

### 17.2 新規アカウント制限

- メール未認証: 編集案を提出できない
- メール認証済み・登録7日未満: 1日3件まで
- 登録7日以上: 初期値として1日10件まで
- 信頼ユーザー: 運用に合わせた上限

### 17.3 適用対象

- カード
- 公演・開催枠
- セットリスト
- 推しプロフィール
- 推し同士の関係
- 公式リンク
- 共有アイコン・共有カラー
- ハッシュタグ

### 17.4 履歴

すべての共有変更について次を記録する。

- 変更前
- 変更後
- 操作ユーザーID
- 操作日時
- 編集案の状態
- 確認結果

通常のカードには投稿者・編集者のHNを表示しない。システム内部では必ずユーザーを追跡できるようにする。一般向け履歴画面でHNを公開するかは将来決定する。

## 18. セットリスト

- 公演単位で登録する
- 曲数を指定すると曲入力行を生成する
- 曲の途中挿入時は表示番号を自動再採番する
- MC、OP、SE、ED、自由入力等は曲番号を増やさない
- 内部では項目の種類と表示順を保持する
- 日付・公演の切り替えはセトリ内のプルダウンを第一候補とする
- 最初の登録は即時公開
- 登録者本人の更新は即時反映
- 他人の更新は共同編集ルールを適用
- 複数公演での同一セトリ共有は将来候補

## 20. 通報と運営管理

### 20.1 通報

ログインユーザーだけが通報できる。

通報対象:

- カード
- URL
- 編集案
- セットリスト
- 推しプロフィール等

通報理由:

- 誤った情報
- 重複したカード
- 不適切な内容
- 危険または不正なURL
- 権利侵害の可能性
- その他

同じユーザーが同じ対象を繰り返し通報できないようにする。通報者が編集者のHNを知る必要はなく、システムが対象の履歴とユーザーを紐付ける。

### 20.2 MVP管理画面

- ユーザー検索・利用停止
- カード、推しプロフィール、URLの非表示
- 通報一覧と対応状態
- 確認待ち編集案の確定・却下
- 重複カードの確認
- カテゴリ管理
- 管理操作履歴

### 20.3 権限

- 管理者: 全設定、ユーザー停止、カテゴリ管理
- モデレーター: 通報、編集案、カード・URLの確認
- 一般ユーザー: 通常機能

開始時は管理者1人とし、将来モデレーターを追加できる。

## 21. アカウントとプライバシー

- MVPではユーザーの公開プロフィールを設けない
- HN、メールアドレス、推し一覧、マイスケジュール、編集実績は他ユーザーから見えない
- アカウント設定は非公開画面とする

アカウント削除時:

- 認証情報を削除
- 推し登録、マイスケジュール、通知設定等の個人データを削除
- 共有カードと採用済み編集は残す
- 履歴上のユーザーを「退会済み」として匿名化
- 未採用の編集案は取り下げる

## 24. 技術構成の第一候補

- フロントエンド: React + TypeScript + Vite
- バックエンド: PHP 8系のJSON API
- データベース: MySQL
- 認証: 同一サイトの安全なセッションCookie
- ローカル開発: Docker Compose
- 本番: さくらのレンタルサーバー
- React: ビルド済み静的ファイルを配置
- PHP: APIとして配置

Dockerは原則としてローカル開発環境に使用し、さくらのレンタルサーバーへDockerコンテナをそのまま配置しない。常駐ワーカー等が必要になった段階でVPS等を再検討する。

## 25. セキュリティ基本方針

- SQL Injection対策としてプリペアドステートメントを使用
- ユーザー入力HTMLをそのまま描画しない
- CSRF対策
- 認証・認可をAPIごとに確認
- セッションCookieへHttpOnly、Secure、SameSite等を設定
- 操作別のrate limit
- 管理画面の厳格な権限確認
- 外部URL取得時のSSRF対策
- 危険URL・不正スキームの拒否
- スワイプ以外の操作手段を用意
